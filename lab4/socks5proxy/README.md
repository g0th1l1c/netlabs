# socks5proxy

Однопоточный SOCKS5-прокси на Go с неблокирующимися сокетами и собственным неблокирующимся DNS-резолвером. Формирование и разбор DNS-пакетов — golang.org/x/net/dns/dnsmessage.

## Возможности

- SOCKS версии 5, команда `CONNECT` (0x01), аутентификация не требуется (метод `0x00`)
- адреса `IPv4` и доменные имена (`0x03`); `IPv6` не поддерживается (ответ `0x08`)
- один поток, один селектор (`epoll`), блокируется только `epoll_wait`
- передача данных одновременно в обе стороны, корректный half-close
- неблокирующий DNS: один UDP-сокет в селекторе, запросы A-записей к рекурсивному резолверу
- ограниченная память на клиента: два буфера по 32 КБ
- нет холостых циклов: событие ожидается, только если действие реально возможно

## Сборка и запуск

Нужны Go 1.26+ и Linux (используется `epoll`). На Windows эту версию можно запускать через WSL.

```sh
make build
./bin/socks5proxy 1080
```

Параметры:

```
socks5proxy <порт>
```

- `<порт>` — порт для входящих подключений клиентов
DNS-резолвер — первый IPv4 nameserver из /etc/resolv.conf.

## Проверка

```sh
# по IP
curl --socks5 127.0.0.1:1080 http://example.com/
# с резолвингом на стороне прокси
curl --socks5-hostname 127.0.0.1:1080 http://example.com/
```

Для браузера укажите SOCKS5-прокси `127.0.0.1:1080` (в Firefox включите «Proxy DNS when using SOCKS v5»). Используйте `127.0.0.1`, а не `localhost`: слушается только IPv4.

Юнит-тесты: `make test`.

## Устройство

```
cmd/socks5proxy/     точка входа, разбор аргументов
internal/poller/     обёртка над epoll
internal/dns/        формирование и разбор dns-сообщений, очередь запросов с таймаутом
internal/proxy/      цикл событий, конечный автомат сессии, буферы, константы протокола
```

Состояния сессии:

```
greeting -> request -> [resolving] -> connecting -> relay
```

- **greeting / request** — байты накапливаются в буфере «клиент → цель», ответы кладутся в буфер «цель → клиент». Данные, пришедшие вместе с запросом, не теряются и уходят цели после подключения
- **resolving** — отправлен DNS-запрос, сессия ждёт ответ в обработчике чтения UDP-сокета; таймаут 5 с, ответ принимается только от адреса резолвера
- **connecting** — неблокирующий `connect`, готовность определяется селектором, результат проверяется через `SO_ERROR`; ошибки отображаются в коды ответа (`0x03`, `0x04`, `0x05`)
- **relay** — двусторонняя пересылка

Как соблюдаются требования:

- **без холостых циклов.** После каждого события маска сокета пересчитывается: `EPOLLIN` — только если в буфере есть место и сторона не закрыта, `EPOLLOUT` — только если есть что отправлять. Сокет без нужных событий снимается с селектора. За событие делается одно чтение или одна запись. При нехватке дескрипторов приём новых подключений приостанавливается; повторная попытка выполняется через секунду ожидания селектора или раньше, при закрытии сессии
- **аккуратное закрытие.** `FIN` от одной стороны передаётся другой через `shutdown(SHUT_WR)` только после опустошения буфера; сессия закрывается, когда обе стороны закончили и буферы пусты
- **ограниченная память.** На клиента — два буфера по 32 КБ; пока буфер заполнен, чтение из соответствующего сокета останавливается, и TCP сам тормозит отправителя
- **производительность.** `TCP_NODELAY` на обоих сокетах, фиксированные буферы переиспользуются

## Ограничения

- только Linux (`epoll`) и только IPv4
- нет аутентификации, поддерживается только `CONNECT` (`BIND` и `UDP ASSOCIATE` отвечают `0x07`)
- нет таймаутов на неактивные соединения и на `connect` (действует системный)



## Проверенные исправления

Регрессионные тесты в internal/proxy/server_test.go проверяют:
- старое событие epoll не закрывает новое соединение с тем же номером fd;
- приём клиентов восстанавливается по таймеру даже без активных сессий.

В обработчике accept нет синхронного логирования. Неустранимая ошибка
возвращается из Run и выводится в main после завершения цикла.

Локальный замер в WSL (медиана трёх передач, 15.11.2026):
- при ограничении отправителя до 100 Мбит/с: 8 МиБ напрямую и через
  прокси передаются примерно за 0,671 с;
- без ограничения: 64 МиБ напрямую — 7,8 мс, через прокси — 19,7 мс.
  На максимальной скорости loopback накладные расходы заметны.
Проверены целостность данных и ответ в обратную сторону после FIN.
Этот замер не заменяет проверку браузера и реальной сети.
