# Places — поиск интересных мест

Консольное приложение на Go. Вы вводите название (например, «Цветной проезд»),
выбираете одну из найденных локаций и получаете **погоду** и **интересные места
рядом с описаниями** — одним общим отчётом.

Лабораторная работа «Асинхронное сетевое взаимодействие».

## Используемые API

| Что делаем                  | Сервис        | Метод                         |
|-----------------------------|---------------|-------------------------------|
| Поиск локаций по названию   | GraphHopper   | Geocoding (`/geocode`)        |
| Текущая погода по координатам | OpenWeatherMap | Current weather (`/weather`) |
| Интересные места в радиусе  | OpenTripMap   | `/places/radius`              |
| Описание места по `xid`     | OpenTripMap   | `/places/xid/{xid}`           |

Нужны три бесплатных ключа (регистрация на сайтах сервисов).
Новые ключи OpenWeatherMap активируются не сразу — иногда до 1–2 часов.

## Быстрый старт

Требуется Go 1.21 или новее. Внешних зависимостей нет.

```bash
cp .env.example .env      # впишите ключи в .env
go run ./cmd/places
```

Ключи можно задать и обычными переменными окружения
(`GRAPHHOPPER_KEY`, `OPENWEATHER_KEY`, `OPENTRIPMAP_KEY`) — они важнее файла `.env`.

Сборка и тесты:

```bash
go build -o places ./cmd/places
go test -race ./...
```

## Как пользоваться

```
Введите название места: цветной проезд
Найдено:
  1. Цветной проезд, Москва, Россия
  ...
Выберите номер (0 — новый поиск): 1
```

`q` — выход. `Ctrl+C` — отмена текущих запросов и выход.

## Настройки (необязательные)

| Переменная         | По умолчанию | Смысл                                      |
|--------------------|--------------|--------------------------------------------|
| `PLACES_RADIUS_M`  | 1000         | Радиус поиска мест, метры                  |
| `PLACES_LIMIT`     | 10           | Сколько мест показывать                    |
| `PLACES_PARALLEL`  | 5            | Сколько описаний запрашивать одновременно  |
| `HTTP_TIMEOUT_SEC` | 10           | Таймаут одного HTTP-запроса                |

## Структура проекта

```
cmd/places/main.go        точка входа: собирает всё вместе и запускает
internal/
  config/                 чтение настроек и ключей (env, .env)
  model/                  простые структуры данных (Location, Weather, Place, Report)
  httpclient/             обёртка над net/http: GET -> JSON, таймаут, ошибки
  api/                    клиенты GraphHopper, OpenWeather, OpenTripMap
  service/                ЛОГИКА: две асинхронные функции + интерфейсы
  ui/                     консольный интерфейс (только ввод/вывод)
```

Зависимости направлены в одну сторону:

```
main -> ui -> service -> model
main -> api -> httpclient
main -> config
```

`service` не знает ни про HTTP, ни про консоль — только про интерфейсы
`Geocoder`, `WeatherProvider`, `PlacesProvider`. Поэтому его можно тестировать
без сети, а консоль при желании заменить на веб-интерфейс, не трогая логику.

## Как выполнены требования задания

Логика оформлена как **две функции**, каждая сразу возвращает канал
с будущим результатом (аналог `CompletableFuture`):

1. `FindLocations(ctx, query) <-chan LocationsResult` — пункт 2 задания.
2. `LoadReport(ctx, location) <-chan Report` — пункты 4 и 5.

| Требование                                   | Как выполнено                                                            |
|----------------------------------------------|--------------------------------------------------------------------------|
| Независимые вызовы работают одновременно     | Погода и список мест стартуют параллельно в двух горутинах               |
| Зависимые вызовы — асинхронная цепочка       | Список мест → описания каждого места (параллельно, не более `PLACES_PARALLEL`) |
| Результаты собираются в общий объект         | `model.Report`; выводится целиком, только когда готов                    |
| Нет блокировок на промежуточных результатах  | Функции возвращают канал сразу; ждёт только `ui` и только конечный результат |

> **Про «асинхронную HTTP-библиотеку».** В Go нет отдельной async-версии HTTP:
> стандартный `net/http` синхронный, а асинхронность достигается горутинами
> и каналами — это штатный и идиоматичный способ. Если преподаватель требует
> именно библиотеку с callback/future-интерфейсом, этот пункт стоит
> согласовать заранее.

## Устойчивость к сбоям

* Не ответила погода — остальной отчёт всё равно показывается.
* Не загрузилось описание одного места — у него пометка, остальные на месте.
* Ключ API никогда не попадает в тексты ошибок.
* Каждый запрос ограничен таймаутом и отменяется по `Ctrl+C`.
* Горутины не «утекают»: результат кладётся в канал с буфером.

## Тесты

`go test -race ./...` проверяет: разбор ответов API (на локальном тестовом
сервере), параллельность (по времени), сохранение порядка мест, частичные
ошибки, лимит одновременных запросов, сценарий работы консоли и то, что
ключ не попадает в ошибки.
